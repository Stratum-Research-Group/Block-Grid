1. [demonstrated] FlashHyperGridEngine computes different routing weights than
   the layer it streams. blockvga/flash_engine.py:47 uses
   softmax(W_c(s_embed) / 0.1): content logits only, hardcoded temperature 0.1.
   The dense reference (blockvga/hyper_tensor_layer.py:146-147) uses
   softmax((W_p(p_embed) + W_c(s_embed)) / tau) with a learnable tau clamped at
   0.05 (default 1.0). The engine's generator interface yields payloads only, so
   the positional term is structurally absent there, and the engine hardcodes
   B=1 (flash_engine.py:32); total_N is accepted but unused. Effect: whenever
   positional logits or tau != 0.1 influence the weights, streamed slot latents
   differ from the dense layer's; this is a route-computation difference, not a
   guaranteed mismatch on every input. The inspected flash-engine test
   (tests/test_flash_engine.py) asserts only output shape and absence of NaN; it
   has no equivalence assertion against the dense layer. Measured (Appendix A,
   run on CPU torch 2.14.1 at this commit, identical weights in both paths):
   max |Z_dense - Z_flash| = 1.9187 against a signal scale of 2.899, with layer
   tau = 1.0 vs the engine's hardcoded 0.1 and the W_p positional term omitted.
   The comparison is on slot latents Z, which is what the engine returns by
   design; the dense reference used in the repro was source-checked against the
   layer's forward steps 1-4.
   Fix: make the engine compute w_write exactly as the core layer does
   (positional embeddings + clamped learnable tau), or document the engine
   explicitly as a content-only approximate router with B=1 support only.
   Gate: repro script passes with diff ~ 0 after the fix.
   https://github.com/Stratum-Research-Group/Block-Grid/blob/261b8b2a8f24bb60f0fc95afd64bab21406a0687/blockvga/flash_engine.py#L47

2. [static] GeneralizedHyperTensorLayer silently ignores num_heads. The config
   exposes num_heads (blockvga/tensor_cell_config.py) and the sibling modules
   (assignment.py:73, hyper_layer.py:65, sparse_hyper_layer.py:92) all reshape
   logits into per-head simplexes, but hyper_tensor_layer.py:147 and :152 take
   softmax over the full K, so num_heads>1 changes nothing in this layer. The
   config's R field is also never read by this layer (no routing_features path).
   Fix: implement the per-head simplex here or raise on num_heads != 1; wire R
   or remove the field.
   https://github.com/Stratum-Research-Group/Block-Grid/blob/261b8b2a8f24bb60f0fc95afd64bab21406a0687/blockvga/hyper_tensor_layer.py#L147

3. [static] UnifiedBlockGrid mode="2d" mishandles a 3-element cell shape. For
   cell_tensor_shape=(P, Q, F) the third entry is dropped at config time and F
   is forced to 1 (blockvga/unified.py:63-69). A matching 6-D input
   [B,H,W,P,Q,F] then passes the dim checks untouched (only dims 4 and 5 are
   reshaped, unified.py:109-113) and fails later on a bare assert inside
   BlockGridLayer.forward (layer.py:50) instead of a clear configuration error;
   a 5-D input is silently interpreted as F=1. Separately, the output squeeze
   test (unified.py:115) compares the raw argument against a tuple, so passing
   cell_tensor_shape as a list returns a 6-D tensor with a trailing F=1 axis.
   Fix: validate cell_tensor_shape length in 2d mode with a clear error (or
   plumb F through), and normalize the argument to a tuple at entry.
   https://github.com/Stratum-Research-Group/Block-Grid/blob/261b8b2a8f24bb60f0fc95afd64bab21406a0687/blockvga/unified.py#L63

4. [static] The Triton kernels are unreachable from the library. BlockPooling is
   only ever constructed with use_triton=False (repo-wide grep: the flag exists
   only inside pooling.py), so BlockGridLayer / HyperGridLayer /
   UnifiedBlockGrid always run the einsum path; the fused autograd kernel is
   exercised only by tests that call it directly. The README's
   "Triton-Accelerated" badge and Example 4 wording ("evaluated via custom
   Triton autograd kernels") describe integration that is not wired up.
   Fix: expose use_triton through the layer configs, or soften the README.
   Gate: tests/test_triton_kernels.py and tests/test_fused_autograd.py (CUDA).
   https://github.com/Stratum-Research-Group/Block-Grid/blob/261b8b2a8f24bb60f0fc95afd64bab21406a0687/blockvga/pooling.py#L32

5. [static] Triton tests fail collection on torch installs without triton.
   tests/test_triton_kernels.py:4 and tests/test_fused_autograd.py:3 import
   blockvga.kernels / blockvga.autograd_kernel at module top, and those modules
   "import triton" unconditionally (kernels.py:2, autograd_kernel.py:2). On a
   triton-less torch (CPU wheel, macOS) pytest errors at collection instead of
   skipping, despite the CUDA skipifs. CI is unaffected only because the Linux
   CUDA torch wheel bundles triton.
   Fix: pytest.importorskip("triton") before those imports.

12. [docs] "Proposition 1" (Hamming-distance fidelity) is stated without the
    conditions that would make it true. docs/HYPERDIMENSIONAL_GRID.md section 3A
    and the paper section 2.1 claim the dot product of factorized coordinate
    embeddings p(x) = sum_i E_i(x_i) "directly reflects the exact Hamming
    distance". The actual formula gives p(x)^T p(y) = sum_{i,j} E_i(x_i).E_j(y_j),
    which includes cross-axis terms the architecture never constrains. Concrete
    counterexample with D=2, d=1, E_1 = [1, 0], E_2 = [1, 1]:
    p(0,0).p(0,1) = 2*2 = 4 while p(0,0).p(1,0) = 2*1 = 2, but both pairs have
    Hamming distance 1. The construction CAN represent Hamming fidelity (choose
    orthogonal axis subspaces with equality-coded axis terms); it is not a
    property of the factorization itself.
    Fix: restate as a trainable desideratum, or add the orthogonality/encoding
    constraint and prove it under that constraint. The underlying architecture
    does not depend on this claim.

13. [static] SyntheticBlockTransportDataset draws from a stateful RNG and
    ignores idx (experiments/dataset.py:41-43). Concrete consequences supported
    by the source: episodes depend on access order and count, and under
    DataLoader(num_workers>0) each worker inherits a copy of the same RNG state,
    producing duplicate episode streams across workers. The committed experiment
    scripts iterate sequentially with one process, so the published results are
    not affected as far as the source shows.
    Fix (only if DataLoader use is planned): derive each episode from a
    per-index seeded generator.

APPENDIX A: REPRO SCRIPT (CPU-safe, tiny shapes, needs only torch)

"""Repro for Block-Grid review finding 1 (Flash engine routing divergence)
and the fp16 numerical probe (open numerical question, not a finding).

CPU-safe, tiny shapes. Needs only torch. Run from the repo root:
    python block-grid-flash-repro.py
Reviewed commit: 261b8b2a8f24bb60f0fc95afd64bab21406a0687
"""
import torch
import torch.nn.functional as F
from blockvga.tensor_cell_config import GeneralizedHyperTensorConfig
from blockvga.hyper_tensor_layer import GeneralizedHyperTensorLayer
from blockvga.flash_engine import FlashHyperGridEngine

torch.manual_seed(0)

cfg = GeneralizedHyperTensorConfig(
    outer_grid=(2, 2, 2),      # D=3, N=8 cells
    cell_tensor_shape=(2, 2),
    K=4, d=8,
    inner_transform=True,
)

layer = GeneralizedHyperTensorLayer(cfg)
engine = FlashHyperGridEngine(cfg, chunk_size=8, device="cpu")
engine.core.load_state_dict(layer.state_dict())  # identical weights

X = torch.randn(1, 8, 2, 2)
B, N, V = 1, 8, 4
flat = X.view(B, N, V)

# --- Dense reference: the routing the layer itself computes ----------------
grids = torch.meshgrid(*[torch.arange(2)] * 3, indexing="ij")
pos = torch.stack([g.flatten() for g in grids], dim=-1).unsqueeze(0)  # [1, 8, 3]
p_embed = sum(emb(pos[..., i]) for i, emb in enumerate(layer.axis_embeds))
s_embed = layer.summary_mlp(flat)
tau = torch.clamp(torch.exp(layer.log_tau), min=0.05)
w_dense = torch.softmax((layer.W_p(p_embed) + layer.W_c(s_embed)) / tau, dim=-1)

G = layer.slotmix.get_mixing_matrix()
Z_dense = torch.einsum("bnv,bnk->bkv", flat, w_dense)
Z_dense = torch.einsum("lk,bkv->blv", G, Z_dense).view(B, cfg.K, 2, 2)
Z_dense = layer.cell_op(Z_dense)

# --- Flash engine path on the same data and weights ------------------------
def gen():
    yield X

Z_flash = engine.forward_streamed(gen, total_N=8)

diff = (Z_dense - Z_flash).abs().max().item()
scale = Z_dense.abs().max().item()
print("=== Finding 1: Flash engine vs dense layer routing ===")
print(f"layer learnable tau: {tau.item():.4f}  (engine hardcodes /0.1, flash_engine.py:47)")
print(f"engine drops the W_p(p_embed) positional term the layer uses")
print(f"max |Z_dense - Z_flash| = {diff:.6f}  (signal scale {scale:.3f})")
print("DIVERGENCE CONFIRMED" if diff > 1e-3 * max(scale, 1.0) else "close on this input")

# --- Finding 8: fp16 softmax without the upcast the sibling modules have ---
print("\n=== fp16 probe: GeneralizedHyperTensorLayer routing in half precision ===")
try:
    layer16 = GeneralizedHyperTensorLayer(cfg).half()
    with torch.no_grad():
        for p_ in layer16.summary_mlp.parameters():
            p_.mul_(40.0)  # force large routing logits
    X16 = torch.randn(1, 8, 2, 2, dtype=torch.float16) * 4.0
    out16 = layer16(X16)
    nan = torch.isnan(out16).any().item()
    print(f"fp16 forward produced NaN: {nan}  (if True: projection logits overflow to inf before softmax; softmax itself max-subtracts and is stable)")
    print("(sibling modules assignment.py:75-76 and sparse_hyper_layer.py:93-94 upcast to fp32 first)")
except Exception as e:
    print(f"fp16 check inconclusive on this torch build: {type(e).__name__}: {e}")
